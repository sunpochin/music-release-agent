## Round 1：讓魔法噴泉可以被檢查

### 1. 內建 mock 發文服務（`tests/fixtures/mock-social-service.js`）

**比喻**：我們的遊樂園有兩個園區：音樂館和廣播站。以前檢查員來驗收時，如果廣播站（姊妹 repo）沒蓋好，整個「音樂館呼叫廣播站」的表演就沒辦法演給他看。
現在我們做了一個**紙箱廣播站**：外觀、按鈕、回話方式都跟真的廣播站一模一樣。檢查員只拿到音樂館的鑰匙，也能看完整場表演。

### 2. 配方書只有一本（`src/dry-run/pipeline-core.js`）

**比喻**：以前做蛋糕的小精靈和檢查蛋糕的檢查員，各自抄了一份食譜。有一天有人改了小精靈的食譜忘了改檢查員的，檢查就會冤枉好蛋糕、放過壞蛋糕。
現在食譜只有一本，大家都讀同一本，誰也不會講錯。

### 3. 檢查員升級：不只看「有沒有蛋糕」，還咬一口（`demo:verify`）

**比喻**：以前檢查員只數「桌上有三個蛋糕盒」就蓋章。但盒子裡可能是空的！
現在檢查員會打開盒子，看蛋糕有沒有草莓（封面圖）、有沒有寫名字（標題）、有沒有插蠟燭（評分）、有沒有附湯匙（聆聽連結），缺一樣就大聲喊「不合格」。

### 4. Golden 測試：把標準答案壓在玻璃下

**比喻**：老師（golden 檔案）把一份滿分考卷壓在講桌玻璃下。每次小精靈交卷，就跟玻璃下的考卷一個字一個字比對。多一個逗號都會被發現。
還準備了三種考題：正常題、怪題（名字全是符號的歌手、空白的曲風）、和陷阱題（壞掉的資料必須讓系統大聲喊救命，不准默默吞掉）。

### 5. 測試不再互相踩腳

**比喻**：以前小朋友們共用同一個沙坑（固定檔案路徑）玩，前一個沒收玩具，下一個就跌倒。現在每人發一個自己的沙坑（暫存目錄＋獨特名字），玩完就整個收走。

## Round 2：把「嘴上說的」變成「做得到的」

### 1. XSS 安檢門有了考試證明（`dashboard/src/utils/markdown.js` + `tests/markdown-renderer.test.js`）

**比喻**：我們一直說大門口有安檢門（HTML 轉義），壞人（惡意腳本）絕對進不來。但說歸說，從來沒有人假扮壞人去測試過！
現在我們把安檢門從牆壁裡拆出來變成獨立的一台機器（純函式模組），然後派了 15 個假壞人去闖關：揹著炸彈的（`<script>`）、藏在圖畫裡的（`<img onerror>`）、躲在標題後面的（`<svg onload>`）……全部被擋下來，而且有考試紀錄（測試報告）為證。

### 2. 警衛排班表寫錯了（CI 的 `feat/*` 分支）

**比喻**：我們請了警衛（CI），但排班表上寫的是「`feature` 街」，我們家其實住在「`feat` 街」。所以警衛從來沒來過我們家巡邏，我們還以為一直有人在看著。
改一行排班表，警衛現在每天都來。

### 3. 警衛巡邏路線補齊

**比喻**：警衛以前只巡大門（`demo:verify`），側門和後門（跨服務驗證、斷線驗證）從來不看。現在三個門每天都巡。

### 4. 丟掉過期的舊玩具

**比喻**：櫃子裡有幾個舊沙坑玩具（過時測試檔案），早就沒人玩了，但偶爾會被路過的測試碰倒，弄得房間看起來很亂（dirty git status）。直接丟掉，並在櫃子上貼「此處不放沙坑玩具」（gitignore）。

## Round 3：兩個服務之間的「包裹規格公告」＋ 真壞人闖真大門

### 1. 契約單一事實來源（`contracts/social-handoff.schema.json`）

**比喻**：音樂館寄包裹給廣播站。以前「包裹該長什麼樣子」是兩邊各自憑記憶：音樂館記得要放卡片（caption），廣播站也記得要收卡片。但如果有一天廣播站偷偷改成要收兩張卡片，音樂館不知道，包裹就會被退件——而且**沒有人會發現是誰的錯**。
現在我們在兩個館之間立了一塊**公告牌**（schema 檔），白紙黑字寫清楚包裹規格。四個人都看同一塊牌子：

- **寄件員**（`server.js` proxy）：寄之前先比對公告，不合格的包裹根本不寄出（回 400）
- **紙箱廣播站**（內建 mock）：收包裹比對公告，而且**自己回信前也先照鏡子**——如果自己的回信不符合公告，立刻大喊（回 500），絕不默默寄出怪信
- **檢查員**（`demo:verify:social`）：把實際寄出和收到的每封信都拿去跟公告比對——不管對面是真廣播站還是紙箱廣播站
- **考官**（`tests/contract/`，17 題）：拿合格和不合格的包裹樣本考公告牌，再把紙箱廣播站真的開起來抽查活的回信

這樣「兩邊悄悄變得不一樣」（契約漂移）這種最難抓的 bug，現在四個地方都會抓到。

### 2. 公告牌的檢查器自己做（`src/services/contract-validator.js`）

**比喻**：市面上有賣豪華檢查機（ajv），但要插電、要安裝（多一個依賴）。我們的公告只有六種包裹，自己做一台手搖式檢查器就夠了，而且整個遊樂園還是維持「不插電也能完整驗收」的招牌。鄰居（姊妹 repo）想用豪華檢查機讀同一塊公告牌？完全可以，公告是標準格式。

### 3. 派真壞人闖真大門（e2e XSS 測試）

**比喻**：Round 2 我們測過「安檢門這台機器」會擋壞人。但機器裝回牆上之後，整棟房子（真實瀏覽器 + 完整前端）還是擋得住嗎？萬一有人從窗戶爬進來呢？
這次我們派壞人**從真的大門走真的流程**：假裝成 AI 歌詞（攔截 API），夾帶五種武器闖進真的 Chromium 瀏覽器。然後檢查四件事：警報器沒響（注入旗標未執行）、壞人被拍成照片貼在牆上展示（payload 變成純文字）、屋裡沒有藏武器（DOM 無危險元素）、沒有彈出奇怪視窗（dialog）。
**已在本機真實瀏覽器實際跑過，不是紙上談兵。**

## Round 4：Song Page 變成真正的頁面（P0）

### 1. 大客廳分房間（App.jsx 471 行 → 336 行）

**比喻**：App.jsx 以前是「什麼家具都堆在裡面的大客廳」：歌單、AI 翻譯、分享圖卡、社群發文……全部擠在一起。
現在三位工作人員搬進自己的房間：

- **歌單送貨員**（`hooks/useAlbumTracks.js`）：負責叫貨、防舊貨蓋新貨、防重複叫貨
- **AI 翻譯員**（`hooks/useTrackAi.js`）：負責歌詞翻譯與賞析、防答非所問、換歌先擦黑板
- **單曲房間的管家**（`components/SongPage.jsx`）：負責決定客人現在該看到什麼

客廳只剩下它真正該管的事：路由、專輯選取、分享圖卡、發文。
每個房間的工作守則（stale-response 防護等）都原封不動搬過去，行為一模一樣。

### 2. 管家的四道檢查（三態 + 友善 404）

**比喻**：以前送貨員摔倒（API 失敗），客人看到的是「無曲目資料」，還以為專輯是空的；
歌單還在路上時，畫面會突然跳動；拿著過期門票（壞掉的分享連結）的客人會看到一片空白。
現在管家依序檢查：

1. 送貨員摔倒了嗎？→ 給「再試一次」的門鈴（錯誤卡 + retry）
2. 歌單還在路上嗎？→ 掛「整理中」的牌子（骨架屏，預告內容形狀，畫面不跳動）
3. 門票過期了嗎？（URL 的歌曲 ID 不在專輯裡）→ 友善地說「找不到這首歌」並推薦同專輯其他歌 — **舊分享連結永遠不會死**
4. 都沒問題 → 請進

### 3. 新考題：直接從門牌進來（deep link e2e）

**比喻**：以前的考試只測「從大門進來、一路點到歌曲」。但朋友傳給你的連結是「直接出現在房間門口」！
新增兩道考題：直接開 `/album/x/song/y` 必須正常渲染；開一個不存在的歌曲連結，必須看到友善的推薦頁、點推薦能跳到正常頁面。

## Round 5：分享體驗（P1）— 門口的海報與抄門牌按鈕

### 1. OG meta 分享端點（`src/services/share-meta.js` + `server.js`）

**比喻**：我們的房子是「進門後才開始畫畫」的畫廊（CSR/SPA）。
郵差（FB/Threads/LINE 的爬蟲）送邀請卡時**不會進門等畫完**，只看門口 — 所以以前分享連結出去，朋友看到的是一張白紙，像垃圾訊息。
現在我們在門口貼好**海報**（`GET /album/:id/song/:id` 回帶 `og:title`、`og:image`、`og:description` 的輕量 HTML）：
郵差拍海報轉發，真人按門鈴（點連結）則被立刻帶進門（meta refresh 導向 SPA）。
海報上的字（專輯名、藝人名、歌名）全部先過安檢門（HTML 轉義）— 跟前端同一套「外部資料一律不可信」哲學，因為歌名是 Spotify 來的外部資料，理論上可以藏壞人。
找不到專輯的過期連結 → 回 404 但仍有通用海報和導向，**不會死路**。

考卷：`tests/share-meta.test.js` 8 題（正常海報內容 / 過期連結退回通用海報 / 海報上藏壞人全部被轉義），加一條 e2e 用爬蟲視角直接打後端驗證活的回應。

### 2. 抄門牌按鈕（CopyLinkButton）

**比喻**：手機有「分享」魔法棒（navigator.share，之前做的 iOS 圖卡分享），但電腦常常沒有。
現在電腦的客人有一個「抄門牌」按鈕：按一下把目前房間的門牌號碼（URL）抄進口袋（剪貼簿），按鈕會亮綠勾勾說「已複製」兩秒。剪貼簿不可用時（非 HTTPS）退回彈出視窗讓你手動複製。
考卷：e2e 授權剪貼簿權限、點按鈕、真的去剪貼簿裡讀出來比對連結。

## Round 6：互動亮點（P2）＋ 一隻被測試曝光的真 bug

### 1. 每首歌專屬的確定性音波（`utils/waveform.js` + `WaveformVisualizer`）

**比喻**：每首歌都有自己的「指紋」（trackId）。我們把指紋丟進一台確定性的「波浪製造機」（seeded PRNG）：同一個指紋進去，**永遠**跑出同一條波浪。不用聽歌也能長出這首歌專屬的樣子，而且這台機器不插網路線，永遠不會故障。
**刻意不用真實音訊**：Spotify 的 30 秒試聽和音訊分析 API 已棄用/不穩定，demo 當天可能翻車。「選永遠不會壞的視覺化」這個取捨本身就是設計的一部分。
考卷：單元測試鎖定確定性（同 seed 同波形、不同 seed 不同波形、高度範圍）；e2e 在真瀏覽器驗證切歌時波形跟著變、切回來波形一模一樣。

### 2. 鍵盤遙控器（`hooks/useTrackKeyboardNav.js`）

**比喻**：房間裡多了一支遙控器：按 `j`（或 ↓）下一首、`k`（或 ↑）上一首，手不離鍵盤逛完整張專輯。
兩條安全守則：客人正在打字時遙控器自動失靈；已經在第一首/最後一首就不動，不會掉出懸崖。
無障礙配套：曲目清單加上 `aria-current` 標記目前的歌、`aria-label` 說明快捷鍵。

### 3. 歌詞逐行進場（純 CSS stagger）

**比喻**：AI 歌詞不再「啪」一聲全部砸在臉上，而是像簾子一樣前 12 行依序輕輕飄進來（之後的立即顯示，不讓人等）。
**尊重暈車的客人**：系統開了「減少動態」（prefers-reduced-motion）的使用者，所有動畫自動關閉。

### 4. 🐛 測試曝光的真 bug：歌單永遠「讀取中」

**比喻**：歌單送貨員有一本「已叫貨登記簿」（prevAlbumIdRef，防重複叫貨）。
但有一種狀況：訂單才剛寫進登記簿、貨還沒送到，整筆訂單就被取消了（React StrictMode 會故意把每個房間「快速拆掉再蓋一次」來抓這種蟲）。
取消時登記簿**忘了擦掉**那筆記錄 — 下一位送貨員翻開登記簿說「咦，叫過了呀」就不再叫貨，但第一批貨早就被丟掉了。結果：畫面永遠卡在「讀取歌曲中...」。
修法一行入魂：取消訂單時，如果貨還沒送到，就把登記簿上那筆擦掉，下一輪自然會重新叫貨。
**這隻蟲是從原版 App.jsx 繼承的**，潛伏到 deep-link e2e 測試（直接開單曲連結）才現形 — 這正是「寫測試曝光既有 bug」的活教材。修完連跑三次全套 e2e 全綠。

## Round 7：UX 體檢（資深 PM 視角）— 給客戶看得出手的畫面

### 1. 專輯頁不再催促客人（AlbumInfo 置中展示）

**比喻**：以前客人才剛走進唱片行、拿起一張專輯，店員就衝過來說「要不要幫你翻譯歌詞？按這裡！」— 客人根本還沒決定要聽哪首歌。
現在專輯頁只做一件事：**把專輯名片好好置中擺出來**（封面、發行資訊、AI 介紹、完整曲目清單）。客人自己點了歌，才進入歌曲頁。
`MetadataPanel` 也正名為 **`AlbumInfo`**，兩種擺法：專輯頁置中放大（`variant="full"`）、歌曲頁縮成側欄（`variant="compact"`），手機上直向堆疊（mobile first）。

### 2. 工程師的儀表板收進後台（移除系統偵錯資訊）

**比喻**：餐廳的瓦斯表、電表很重要，但要裝在廚房，不是貼在菜單上。
「HTTPS 安全連線 / 原生分享 API / 分享圖卡狀態」這些是開發時的偵錯資訊，出現在消費者畫面上就像後台忘了關 — demo 或面試時最扣分的一種細節。已整塊移除。

### 3. 選歌即上菜（自動載入歌詞）— 回答「SongInfo 該跟用戶怎麼互動」

**產品決策**：歌曲頁的主菜就是歌詞。客人點了菜（選了歌）就直接上菜，
不要再遞一張菜單要求「按『尋找歌詞』才出餐」— 那是把系統的工作推給用戶。
所以：

- **歌詞 = 主菜 → 自動載入**：選歌瞬間就開始煮（loading 動畫），煮好直接上桌
- **AI 賞析 = 現做甜點 → 保留手動**：它比較重、不是每個人都要，
  保留「開始歌曲 AI 賞析」按鈕，給用戶明確的選擇權 — 這就是漸進式揭露（progressive disclosure）
- 自動載入失敗時有低調的「重新載入歌詞」入口，不會死路

同一首歌只自動叫一次菜（autoFetchedRef 防 StrictMode 重複），換歌會先擦黑板再上新菜。

## Round 8：冷凍庫與遙控器升級（歌詞快取 + 手機兩層返回）

### 1. 歌詞翻譯冷凍庫（Obsidian 相容快取）

**比喻**：以前每位客人點同一道菜，廚師（Gemini）都要重新開火現做 — 又慢又燒錢（token）。
現在廚房有**冷凍庫**（`data/lyrics-cache/`）：做過的菜貼上標籤冰起來，下次同一道菜直接解凍上桌（毫秒級、零 token）。
標籤是人看得懂的字條（Markdown + frontmatter），所以整個冷凍庫可以直接搬進你的筆記櫃（把 `LYRICS_CACHE_DIR` 指到 Obsidian vault），每道菜變成一則可搜尋的筆記。

**什麼時候丟掉冷凍的菜？** 答案是：幾乎永遠不用！歌詞不會變（不可變內容），所以沒有「過期時間」。
只有兩種情況會重做：**食譜改版**（`PROMPT_VERSION` +1，舊菜自動視為過期）和客人說**「我要現做的」**（force refresh）。

### 2. 兩位廚師（LYRICS_PROVIDER=gemini|ollama）

**比喻**：主廚是 Gemini（手藝好、按次收費），二廚是 Ollama（住你家、免費、手藝普通）。
用環境變數選廚師，兩人讀**同一本食譜**（lyrics-prompt.js 單一事實來源），不會各做各的口味。
重要取捨：**預設仍是 Gemini** — 如果把二廚設成預設，評估者 clone 下來（家裡沒有 Ollama）就吃不到菜了。

### 3. 路過的歌不叫菜（400ms debounce）

**比喻**：客人用遙控器（j/k）快速轉台時，不能每轉一台就叫一道菜 — 會做出一整排沒人吃的菜（被丟棄的請求，token 照燒）。
現在規則是：**停下來看的那一台才上菜**（停留 400ms 才呼叫 API）。

### 4. 手機返回鍵學會「一層一層走」

**比喻**：以前手機上只有「直接回大門」的按鈕。現在是「回上一層」：
